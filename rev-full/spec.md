# Спецификация: полный PTG — текст, код, метадерево с графом, любые эмбеддинги

Пакет `ptgfull`. Собирает память проекта из готовых частей; своё — только склейка и решения между ними.

| часть | берём готовое | своё |
|---|---|---|
| приём текста | `memshell.convert` (MarkItDown), `memshell.atomize` (абзацы, Chonkie для длинных), `memcore.scrub` (detect-secrets) | — |
| хранилище, поиск по смыслу и словам | LanceDB: таблица на пространство векторов, полнотекстовый индекс | раскладка таблиц |
| любые эмбеддеры | реестр эмбеддеров LanceDB (sentence-transformers, openai и совместимые серверы, ollama, huggingface, jina, cohere, gemini, voyageai …) | проверочный эмбеддер `hash` |
| перенос запроса между моделями | Drift-Adapter: ортогональный Прокруст `scipy.linalg.orthogonal_procrustes`, иначе `numpy.linalg.lstsq` | — |
| слияние мест | RRF (Cormack 2009, k = 60) | — |
| граф кода | codebase-memory-mcp 0.11.0 целиком, чтение через `cli query_graph` | разбор его ответа |
| обход графа | личный PageRank `networkx.pagerank` с затравкой из находок (HippoRAG) | — |
| метадерево | — | дерево «папка → файл → символ», атомы по источникам, швы «атом ↔ код» по происхождению |

## Пользовательские истории

### P1. Любые эмбеддинги
Пользователь подключает к одной базе несколько пространств векторов от разных моделей, в том числе готовую базу,
посчитанную чужой моделью, без пересчёта.

Сценарии приёмки:
1. Дано: пространство `h=hash:words@16`. Когда: `index` принимает заметку. Тогда: у каждого атома есть вектор
   этого пространства.
2. Дано: база с векторами модели, которой сейчас нет. Когда: есть пары атомов, посчитанные в обеих моделях. Тогда:
   `bridge` строит адаптер, и запрос идёт в эту базу через модель, которая есть.
3. Дано: у пространства нет ни модели, ни адаптера. Когда: приходит запрос. Тогда: пространство пропускается, поиск
   по словам работает.

### P2. Кодовый PTG
Граф кода строит codebase-memory-mcp; ptgfull берёт из него символы (Function, Method, Class) и рёбра CALLS, USAGE.

Сценарии:
1. Дано: путь к репозиторию и к программе codebase-memory-mcp. Когда: `index` с `repo`. Тогда: символы и рёбра
   лежат в базе, у символа — файл и строки.
2. Дано: программы нет по пути. Тогда: `FileNotFoundError`, база не портится.

### P3. Метадерево
Дерево «папка → файл → символ» для кода и «источник → атом» для текста. Его сшивают с кодом рёбра по происхождению:
* `edits` — атом переписки правит файл: `[инструмент Edit: путь]`, `Write`, `MultiEdit`, `NotebookEdit`;
* `reads` — `[инструмент Read: путь]`;
* `mentions` — атом называет файл или символ.

Сценарии:
1. Дано: атом `[инструмент Edit: H:\p\memcore\filtering.py]` и файл кода `memcore/filtering.py`. Тогда: ребро
   `edits` от атома к `file:memcore/filtering.py`.
2. Дано: атом называет `filtering.admit`, а такой символ один. Тогда: ребро `mentions` к символу.
3. Дано: короткое имя `run` есть у двух символов. Тогда: шва нет, неоднозначное не угадываем.

### P4. Обход и подсказка
Поиск по всем доступным пространствам и по словам, слияние RRF, затем личный PageRank по метадереву от найденного.
Ответ — блок `<ptg-context>` в бюджете символов: атомы текстом, код — ссылкой «вид, имя, файл:строки».

Сценарии:
1. Дано: база из сценария P1.1. Когда: `ask` со словами одной заметки. Тогда: этот атом в блоке первым.
2. Дано: базы нет. Тогда: пустая строка.

### P5. Текстовый PTG
Файлы любых форматов MarkItDown, вычистка секретов до записи, атом — абзац. Повторный приём того же файла не
плодит копий: id атома — отпечаток `memshell.atomize`.

## Требования

* ФТ-001. КОГДА задано пространство строкой `имя=поставщик:модель@размерность`, СИСТЕМА ДОЛЖНА разобрать её в
  `Space`: поставщик — до первого «:», размерность — после последнего «@».
* ФТ-002. КОГДА приходит запрос, СИСТЕМА ДОЛЖНА для каждого пространства базы выбрать путь: `direct`, если модель
  доступна; иначе `adapter` от первого доступного источника, для которого есть адаптер; иначе пространство пропустить.
* ФТ-003. Для любых списков находок СИСТЕМА ДОЛЖНА сливать их RRF: оценка = Σ 1/(k + место), место с 1, оценка
  округляется до 6 знаков; порядок — по оценке, при равенстве — по id; `via` — из первого списка, где id встретился.
* ФТ-004. СИСТЕМА ДОЛЖНА иметь проверочный эмбеддер `hash`: слова `\w+` в нижнем регистре, корзина = первые 8 байт
  blake2b слова (big-endian) по модулю размерности, счёт слов, нормировка L2, округление до 6 знаков, −0.0 → 0.0;
  пустой текст — нулевой вектор.
* ФТ-005. КОГДА есть пары векторов двух моделей, СИСТЕМА ДОЛЖНА строить адаптер: при равных размерностях —
  ортогональный Прокруст, иначе — наименьшие квадраты; числа до 6 знаков, −0.0 → 0.0.
* ФТ-006. КОГДА codebase-memory-mcp отвечает таблицей, СИСТЕМА ДОЛЖНА разобрать строки, раскрывая ссылки
  `@N+хвост` по блоку `rows_refs`, и отбросить узлы и рёбра вне проекта (`builtins.len`, `<python-builtins>`).
* ФТ-007. СИСТЕМА ДОЛЖНА строить рёбра дерева `contains`: `dir:` (корень) → `dir:a` → `dir:a/b` → `file:a/b/x.py` →
  символ; для текста — `src:<файл>` → атом и `next` между соседними атомами одного файла по порядку.
* ФТ-008. СИСТЕМА ДОЛЖНА сшивать атом с файлом кода, только если путь из атома оканчивается на `/<путь файла>` или
  равен ему, после замены `\` на `/`; из нескольких подходящих берётся самый длинный, при равной длине — шва нет.
* ФТ-009. СИСТЕМА ДОЛЖНА сшивать атом с символом, только если имя однозначно: полное имя или хвост полного имени
  с точкой (`filtering.admit`), либо короткое имя в обратных кавычках или перед «(», которое есть ровно у одного символа.
* ФТ-010. Для любого графа и затравки СИСТЕМА ДОЛЖНА возвращать соседей по личному PageRank: без затравки, без узлов
  `dir:` и `src:`, по убыванию оценки, при равенстве — по id, не больше лимита.
* ФТ-011. Для любых кусков СИСТЕМА ДОЛЖНА собирать блок не длиннее бюджета, куски целиком, по порядку; не влез
  первый — пустая строка.
* ФТ-012. КОГДА база пуста или её нет, `ask` ДОЛЖЕН вернуть пустую строку.

## Сущности
`Space`, `Hit`, `Route`, `CodeNode`, `Edge`, `Atom`, `Piece`, `Counts` — в `ptgfull/types.py`.

Узлы графа:
* атом — его id;
* символ — полное имя без префикса проекта;
* файл кода — `file:<путь>`;
* папка — `dir:<путь>`;
* источник текста — `src:<файл>`.

## Хранилище (LanceDB в папке `home`)

| таблица | что в ней |
|---|---|
| `spaces` | пространства |
| `atoms` | атомы и полнотекстовый индекс по `text` |
| `vec_<имя>` | id и вектор, по таблице на пространство |
| `code_nodes`, `code_edges` | граф кода |
| `edges` | все рёбра метадерева |
| `adapters` | источник, цель, матрица |

Запись атомов и векторов — upsert по id. Код и рёбра заменяются целиком.

## Крайние случаи
* пустая база или её нет;
* пространство без модели;
* файл без текста;
* абсолютные пути Windows в переписке;
* одинаковые короткие имена символов;
* ответ codebase-memory-mcp постранично по 200 строк (`SKIP n LIMIT 200`, пока строк 200).

## Допущения
* Подключение к демону PTG-MEM и перенос store_v6 — после «да» пользователя, вне этого пакета. Готовая база
  подключается через `attach` (атомы и векторы уже посчитаны).
* Реранкер и MCP-сервер — потом.
* Модели загружает реестр LanceDB. Сеть и ключи — только из окружения.

## Критерии успеха
* Все проверки kit зелёные; `python -m pytest` в папке проекта проходит.
* На PTG-MEM/rev: символов из codebase-memory-mcp не меньше 46 функций; швы `edits` есть у каждого файла кода,
  который правили в переписке.
* Подсказка `ask` укладывается в бюджет на любом запросе.
